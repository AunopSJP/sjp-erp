## รายละเอียดรายหัวข้อ

### 1. Navigation & Modularity
ทำแล้ว
- `/apps` App Launcher: รายการโปรด → เปิดล่าสุด → โมดูลทั้งหมด, การ์ด 24 ต่อหน้า + โหลดเพิ่ม, ค้นชื่อไทย/อังกฤษ/alias, กรองหมวด, สถานะว่าง/โหลดไม่ได้/ค้นไม่พบ, ปุ่มล้างคำค้น
- `GET /api/meta` กรองโมดูลที่ผู้ใช้ไม่มีสิทธิ์อ่านออกจาก `entities`/`customModules`/`workflows`/`resources`; e2e ตรวจทั้งกรณีให้สิทธิ์และถอนสิทธิ์
- Sidebar แสดงเฉพาะหมวดของโมดูลปัจจุบัน, จำกัดสิทธิ์, จำสถานะพับ/โปรด/ล่าสุดแยกตามผู้ใช้, ปุ่ม "แอปทั้งหมด" ทุกหน้า, คืนโฟกัสเมื่อปิดบนจอแคบ
- ลิงก์ตรงที่ไม่มีสิทธิ์ → `/apps` พร้อมข้อความกลาง `ไม่พบรายการหรือคุณไม่มีสิทธิ์เข้าถึง`

ยังเหลือ
- Module lifecycle **ร่าง/เผยแพร่/เก็บถาวร** ที่ระดับโมดูล (`status`): draft/archived ถูกตัดจาก `/api/meta`, `/api/search` และเปิดลิงก์ตรงไม่ได้ (`/api/records`, `/api/meta/entity`, `/api/meta/options`, `/api/views` → 403) ทั้งผู้ใช้ทั่วไปและผู้ดูแล; `/api/meta/config` ยังเห็นเพื่อจัดการ; Module Builder มีปุ่มเผยแพร่/ย้ายเป็นร่าง/เก็บถาวร และสร้างโมดูลใหม่เป็นร่างโดยค่าเริ่มต้น
- e2e ครอบ: สร้าง draft → ไม่เห็น/เปิดไม่ได้ → publish → ใช้ได้และค้นเจอ → archive → หายและแก้ไม่ได้ → สถานะผิด 400 (`server/test/acceptance.e2e-spec.ts`)
- **alias โมดูลที่ผู้ใช้แก้เองได้**: `aliases[]` สูงสุด 20 คำ (ตัดช่องว่าง/ซ้ำแบบไม่สนตัวพิมพ์), แก้ใน Module Builder, ใช้ค้นใน App Launcher/ช่องค้นหาเมนู; e2e ตรวจ normalize/limit และเบราว์เซอร์ค้น “ใบสั่งซื้อ” เจอโมดูลที่ตั้ง alias ไว้

ยังเหลือ
- Workspace หลายองค์กร: **ทำตามแบบ A ครบแล้ว** — ตาราง `workspaces` + `user_workspaces`, `active_workspace_id` ต่อผู้ใช้, header `X-Workspace-ID` ตรวจ membership ทุกคำขอ, scope ข้อมูลด้วย `workspace_id` (records, saved_views, audit, events, approvals, files), เลขเอกสารแยกต่อ Workspace (unique index เป็น `workspace_id+entity+code`), ตัวสลับ Workspace ใน topbar, หน้าจอ Workspace ใน Settings (สร้าง/สลับ/เก็บถาวร/ตั้งสมาชิก), สำรอง–กู้คืนพา Workspace และ membership ไปด้วย, backfill ข้อมูลเดิมเข้า `default`; e2e ยืนยันแยกข้อมูล/สิทธิ์/เพิกถอน/เลขเอกสารซ้ำข้าม Workspace ได้/restore; ตรวจบนเบราว์เซอร์จริง: เปิด `/settings?tab=workspaces` เห็นตาราง, สร้าง “สาขาที่ 2” จาก UI สำเร็จ, topbar ขึ้นตัวสลับ 2 รายการ, เปิดสมาชิกเห็นรายชื่อผู้ใช้, สลับแล้ว `localStorage` และ topbar ตรงกัน; อัปเกรดฐานข้อมูลเดิม: counter/unique index ถูกย้ายมาเป็นราย Workspace โดยข้อมูลเดิมอยู่ครบ; ข้อจำกัดที่ตั้งใจ: โมดูล/Workflow/บทบาทยังใช้ร่วมทุก Workspace, webhook/คิวแจ้งเตือนยังเป็นระดับระบบ
- alias ที่ผู้ใช้แก้เองได้ (ตอนนี้รวมชื่อไทย/อังกฤษ/key/description ในตัว)
- ทดสอบภาระจริงที่ 501 โมดูล: **ผ่านแล้ว** ด้วย `server/test/acceptance.e2e-spec.ts` — สร้าง 501 โมดูลในฐานข้อมูลทดสอบ (4.66 วิ), admin เห็น/เปิด Dataset/สร้างรายการได้, viewer ไม่เห็นใน `/api/meta`, เปิด `/api/records`, `/api/meta/entity`, `/api/meta/options`, `/api/views` ถูกปฏิเสธ 403; ให้สิทธิ์แล้วเห็นทันทีและถอนแล้วหาย (UI Launcher มี unit test 501 การ์ด/ค้นหาเจอ test501)

### 2. Multi-View Architecture
ทำแล้ว
- Grid แบบ server-side: ค้น/กรอง/เรียง/แบ่งหน้าจากทั้งชุดตามสิทธิ์, เรียงหลายคอลัมน์ + NULL ท้าย + tie-break ด้วย id, ตัวกรองกลุ่ม AND/OR (`where`), ตรึงหัวตารางและคอลัมน์รหัส, ชิดขวาตัวเลข, ตัวคั่นหลักพัน
- Inline Editing: F2/Enter/ดับเบิลคลิก, Enter/Tab ยืนยัน, Esc ยกเลิก, ไม่บันทึกเมื่อคลิกออก, editor ตามชนิด, ตรวจค่าฝั่งเซิร์ฟเวอร์, optimistic concurrency (`_expectedUpdatedAt` → 409) พร้อมเทียบค่าล่าสุด/ค่าที่กรอก, announce + คืนโฟกัส, จัดการกรณีแถวหลุดจากผลกรอง
- Form: เตือนร่างค้างก่อนปิด/เปลี่ยนหน้า (canDeactivate + beforeunload), ส่งเฉพาะค่าที่เปลี่ยน, ตรวจสถานะก่อนส่งซ้ำเมื่อเครือข่ายขาด
- Kanban: เลนตาม workflow, การ์ด 2–4 ฟิลด์, ลากหรือเมนู "ย้ายไปสถานะ…" ใช้กฎเดียวกัน, ปฏิเสธแล้วกลับเลนเดิมพร้อมเหตุผล, ซ่อนเป้าหมายที่ต้องสิทธิ์ปิด, โหลดเพิ่มต่อเลน, จำกัดเฉพาะรายการที่อ่านได้
- สลับมุมมองไม่คัดลอกตัวกรองกัน; Saved View แยกตามชุดข้อมูล

ทำแล้วเพิ่มเติม
- Saved View เก็บฝั่งเซิร์ฟเวอร์แล้ว (`saved_views`): `เฉพาะฉัน` ทุกคนมี, `แชร์กับทีม` เฉพาะผู้มีสิทธิ์แก้การตั้งค่า, ชื่อซ้ำถูกปฏิเสธ, ตรวจฟิลด์/คอลัมน์/เงื่อนไขกับชุดข้อมูลและตัดฟิลด์ sensitive, การแชร์ไม่ให้สิทธิ์อ่านข้อมูลเพิ่ม
- ป้าย `ยังไม่บันทึกมุมมอง` ทำงานเทียบสถานะปัจจุบันกับมุมมองที่ใช้อยู่ และคืนตำแหน่งด้วย Record ID ที่เปิดล่าสุดของมุมมอง (ถ้าไม่อยู่ในผลลัพธ์จะโฟกัสหัวมุมมองพร้อมบอกเหตุผล)
- **ครบทุกหน้าหลักแล้ว**: Ticket, PM (งานตามรอบ/แผน) และคลัง (การเคลื่อนไหว) ผูก `viewsEntity` ใช้ Saved View ฝั่งเซิร์ฟเวอร์แบบเดียวกับ `/entities` และใบสั่งซื้อ
- **ซ่อม View อัตโนมัติ**: เมื่อฟิลด์/คอลัมน์ในมุมมองใช้ไม่ได้ ระบบตัดเฉพาะส่วนนั้น (ตัวกรอง/เรียง/ซ่อนคอลัมน์/กลุ่ม/เงื่อนไข) พร้อมแจ้งจำนวนที่ตัด แทนการปล่อยให้คำขอถูกปฏิเสธ; unit test `view-config.spec.ts` 5 เคส
- **ส่งออก/คัดลอกทั้งชุดที่กรองแล้ว** ในโหมด server-side: ดึงหน้าละ 500 ต่อเนื่องจนครบ (เพดาน 10,000 แถว/ครั้ง พร้อมแจ้งเตือน) แทนการส่งออกเฉพาะหน้าปัจจุบัน; unit test `list-export.spec.ts` 3 เคส และวัดจริงที่ 100k (ดู §4)

ทำแล้วเพิ่มเติม
- Saved View ฝั่งเซิร์ฟเวอร์ครอบ Ticket/PM/คลังแล้ว (เดิมเหลือเฉพาะ `/entities` และใบสั่งซื้อ)
- ระบบซ่อม View อัตโนมัติเมื่อฟิลด์ถูกถอดสิทธิ์/ถูกลบ (ตัดเฉพาะส่วนที่ใช้ไม่ได้ + แจ้งจำนวน)
- ส่งออก/คัดลอก CSV ครอบทั้งชุดที่กรองแล้วในโหมด server-side (เพดาน 10,000 แถวต่อครั้ง)

### 3. Dynamic Field & Schema UI
ทำแล้ว
- Drawer (540 px จอใหญ่ / bottom sheet จอแคบ) เปิดจาก `+ เพิ่มฟิลด์` ท้ายหัวตาราง และปุ่ม `จัดการฟิลด์`; ฟิลด์ focus เริ่มที่ชื่อ, Esc ปิด, คืนโฟกัส, เตือนทิ้งร่าง
- ตรวจชื่อว่าง/ซ้ำ (ตัดช่องว่าง ไม่สนตัวพิมพ์), ID ถาวรแยกจากป้ายชื่อ, ชนิดระยะแรกตามสเปก, ตัวเลือกสำหรับ select, Relation + ลิงก์ย้อนกลับแบบ atomic (สำเร็จทั้งคู่หรือไม่เปลี่ยนทั้งคู่), ปฏิเสธโมดูลระบบ
- `บังคับกรอก` แสดงจำนวนรายการเดิมที่ยังไม่มีค่าก่อนยืนยัน
- ตัวเลือกมี **ID ถาวร + ป้าย + สี + เก็บถาวร** (`optionMeta`, backward-compatible กับ `options` เดิม): รูปแบบฟอร์ม/ตัวกรองใช้ป้ายจาก meta, ตัวเลือกเก็บถาวรแสดงได้แต่เลือกใหม่ไม่ได้ (เซิร์ฟเวอร์บล็อกตอนสร้าง/เปลี่ยนค่า), ตรวจ id ซ้ำ/สีที่ไม่รองรับ/ไอดีที่ไม่อยู่ในรายการ
- Relation หลายรายการ (`multiple`) พร้อม `displayField`: เก็บเป็น array ของ id, ตรวจ ≤50/ซ้ำ/ไม่มีสิทธิ์/ไม่มีอยู่, แสดง label จากฟิลด์ที่เลือก, กรอง/ค้นหาแบบ array ได้, และหน้ารายการที่เชื่อมโยง (related) รองรับ array
- เพิ่มคอลัมน์ใหม่เฉพาะมุมมองของผู้สร้าง (localStorage) ไม่เปลี่ยนเลย์เอาต์คนอื่น; API audit ทุกครั้ง

ทำแล้วเพิ่มเติม
- **สิทธิ์ต่อตัวเลือก (option-level ACL)**: `optionMeta[].roles` จำกัดบทบาทที่เลือกได้; `/api/meta` และ `/api/meta/entity` กรองตัวเลือกตามบทบาท (ผู้ดูแลเห็นทั้งหมด), เซิร์ฟเวอร์ปฏิเสธการเลือกค่าใหม่ที่ไม่มีสิทธิ์, UI ใน Schema Drawer ตั้งสิทธิ์ได้ทั้งตอนสร้างฟิลด์และปุ่ม “ตัวเลือก/สิทธิ์” ของฟิลด์เดิม (เพิ่ม/แก้ป้าย/สี/เก็บถาวร/บทบาท, ลบตัวเลือกที่มีข้อมูลถูกบล็อก) — e2e: viewer ไม่เห็น/เลือก b ไม่ได้ แต่ admin ได้; unit: `meta.service.spec.ts`
- **picker กรองตามกฎธุรกิจ**: `FieldDef.optionFilter { by, targetField }` เช่น `tickets.site` ผูกกับ `customer`; `/api/meta/options/:entity?filterField=&filterValue=` กรองรายการปลายทาง และ UI โหลดใหม่เมื่อค่าต้นทางเปลี่ยน — e2e ตรวจได้เฉพาะไซต์ของลูกค้าที่เลือก + เบราว์เซอร์เห็นคำขอ `filterField=customer` และตัวเลือกเหลือ Site One
- **ฟิลด์**: เปลี่ยนชนิดได้จาก Schema Drawer (`PATCH /meta/entity/:key/field/:field`) พร้อมแปลงค่าและบอกจำนวนค่าที่ล้าง ต้องยืนยันด้วย `confirm` เมื่อมีค่าที่แปลงไม่ได้; เก็บถาวร/คืนสถานะได้โดยไม่ลบข้อมูล (ซ่อนจากฟอร์ม/ตัวกรอง, validation ข้ามฟิลด์ที่เก็บถาวร)
- **ผลกระทบก่อนแก้**: `field-impact` คืนจำนวนรายการ + ชื่อ Saved View ที่ใช้ฟิลด์ + workflow ที่บังคับฟิลด์ แสดงใน Drawer
- **Relation หลายรายการสองทาง (many-to-many)**: สร้างลิงก์ย้อนกลับแบบ `multiple` ได้ ฝั่งย้อนกลับเป็น read-only และซิงก์อัตโนมัติเมื่อสร้าง/แก้/ยกเลิก/กู้คืนรายการ (e2e ตรวจทั้ง 4 จังหวะ)
- **Option/Workflow**: การเพิ่ม/ลบ/แก้ตัวเลือกถูกบันทึกเป็น audit `metadata.options`; บันทึก workflow แล้ว labels/colors ถูก sync ลง `optionMeta` ของฟิลด์ `status` ให้ Grid/Kanban ใช้ชุดเดียวกัน

### 4. High Data Density
ทำแล้ว
- ความสูงแถว/ฟอนต์ตามธีมเดิม, ตรึงหัวตาราง + คอลัมน์ระบุ, ตัวเลขชิดขวา tabular, ตัดข้อความหนึ่งบรรทัด (`data-label` สำหรับจอแคบ)
- Grid เลื่อนในพื้นที่ตัวเอง, toolbar ไม่เลื่อนตาม, ปุ่มก่อน/ถัดไปบอกช่วงจากยอดทั้งชุด
- แยกสถานะ `ยังไม่มีข้อมูล` / `ไม่ตรงตัวกรอง` / `โหลดไม่ได้` พร้อมทางออก
- ตัวสร้างเงื่อนไขขั้นสูงแบบ AND/OR (สูงสุด 5 เงื่อนไขหลัก + กลุ่มย่อย 3 เงื่อนไข) พร้อมสรุปวงเล็บที่อ่านได้; ยอดรวมทุกคอลัมน์ตัวเลขและจำนวน/ยอดรวมรายกลุ่มคำนวณจากทั้งชุดที่กรองแล้วฝั่งเซิร์ฟเวอร์ ไม่ใช่หน้าปัจจุบัน
- GRID-01 ระดับ API: `server/test/grid.acceptance.e2e-spec.ts` สร้างชุดข้อมูล 80 ฟิลด์และ 100,000 แถว (seed 928 ms) — หน้า 2 เรียง code 55 ms, หน้าที่ 1000 148 ms, กรอง + ยอดรวม + 4 กลุ่ม 252 ms, ค้นหาเต็มชุด 2.37 วิ; ยอด/จำนวนตรงกับทั้งชุด (ยังไม่ได้ทดสอบ UI กับข้อมูลจริง 100k)

ทำแล้วเพิ่มเติม
- ปรับความกว้าง/ย้ายคอลัมน์: **ทำแล้ว** — ลากหัวคอลัมน์หรือใช้ปุ่ม ←/→ ในเมนู `คอลัมน์`, ปรับความกว้างด้วยการลากขอบหรือลูกศรที่ตัวจับ (โฟกัสได้), จำลำดับ/ความกว้างต่อตาราง และมีปุ่มรีเซ็ต
- แถวกลุ่มแบบ inline: **ทำแล้ว** — เมื่อจัดกลุ่ม 1–2 ระดับ ตารางแสดงแถวหัวกลุ่มพับ/กาง (`aria-expanded`) พร้อมจำนวนและยอดรวมจากทั้งชุด; แถวข้อมูลในหน้านั้นอยู่ใต้กลุ่มของตน
- หลักฐานเบราว์เซอร์ 360 px: หน้ากว้าง 345 px ไม่มี scroll แนวนอนทั้งหน้า, มี 2 แถวกลุ่ม, ตัวจับความกว้างมี `tabindex=0`; ที่หน้าปกติ ลาก/ปุ่มย้ายคอลัมน์และปรับความกว้างด้วยลูกศรถูกบันทึก (`sjp-column-order`, `sjp-column-width`) และคงอยู่หลัง reload
- **ทดสอบ UI จริงกับ 100,000 แถวแล้ว** (seed 80 ฟิลด์): เปิดหน้า → เห็น 25 แถวใน 1.18 วิ (API 678 ms), หน้าถัดไป 215 ms, จัดกลุ่มตาม `grp` 329 ms ได้ 4 กลุ่ม × 25,000 พร้อมยอดรวมทั้งชุด, ค้นหา “Row 050000” เจอใน 3.25 วิ (API 3.17 วิ), ไม่มี scroll แนวนอน, หัวตาราง `position: sticky`; ส่งออกทั้งชุดหยุดที่เพดาน 10,000 แถวใน 27 วิ พร้อมข้อความแจ้ง
- คัดลอก/ส่งออก CSV ครอบทั้งชุดที่กรองแล้ว (ดึงหน้าละ 500, เพดาน 10,000 แถว/ครั้ง)
- GRID-02: ตามที่เจ้าของยอมรับ — ใช้ automated keyboard/focus/validation + Lighthouse แทนการทดสอบ screen reader ด้วยคน: Lighthouse Accessibility = **1.00 (0 failure)**, 200% zoom ตรวจด้วย CSS viewport 500 px (ผลเดียวกับ browser zoom ที่ลด viewport ลงครึ่ง) ไม่มี scroll แนวนอนทั้งหน้า/topbar ยัง sticky/กลุ่มและตัวจับความกว้างใช้ได้, 360 px ไม่มี overflow

## บั๊กที่พบระหว่างตรวจและแก้แล้ว
- Lighthouse (Accessibility 0.95) พบ `role="separator"` ของตัวจับความกว้างไม่มี `aria-valuenow/min/max` → เพิ่มค่าเหล่านี้ วัดซ้ำได้ **1.00 และ 0 failure**
- ปุ่มบันทึก Module Builder ส่ง `workflowKey` (ค่าที่ `/meta/config` เพิ่มให้) กลับไปใน PUT ทำให้ DTO ปฏิเสธ 400 “property workflowKey should not exist” — แก้ด้วยการประกอบ payload เฉพาะฟิลด์ที่ DTO รับ และเพิ่มปุ่มวงจรชีวิตที่ใช้ payload เดียวกัน
- Drawer ใช้คลาส `.side` ชนกับ Sidebar เดิม ทำให้ **โหมดมืดซ่อน Drawer ทั้งแผง** และจอแคบทับตำแหน่งเป็นเมนูข้าง → เปลี่ยนเป็น `.modal-aside`/`.aside-back`; ตรวจซ้ำที่ 360 px โหมดมืด (display flex, ไม่มี overflow แนวนอน) และ 1000 px (กว้าง 540 ชิดขวา)
- ค้นหาข้ามโมดูลเดิมทำ filter ซ้ำซ้อนบนข้อมูลเดียวกันและไม่เคารพ scope ของ Relation → แก้เป็น EXISTS ต่อตารางพร้อม scope
- ตัวกรอง/เรียงที่อ้างฟิลด์ไม่มีอยู่เดิมถูกเมินเงียบ ๆ → เปลี่ยนเป็น 400 พร้อมบอกให้ปรับมุมมอง
